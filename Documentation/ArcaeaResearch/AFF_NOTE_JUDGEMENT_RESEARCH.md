# AFFノート構造・判定点 調査記録

## 目的と結論

調査日: 2026-09-05

MAGATU TEMPO FORGEは当面`timing(...)`の生成だけを扱う。ただし、既存譜面へ安全に統合するには、タップ、ロング、アーク、アークタップ、トレース、タイミンググループと、ゲーム上の判定点の関係を理解しておく必要がある。

今回、次の4系統を突き合わせた。

1. ArcCreateの実装（commit `755c2e8818dab3c8404b3ff997e87373607891cd`）
2. Arcade Plusの実装（commit `d157e35cbc3af869094775333a89cf0918aac166`）
3. VSCode Arcaea File Format拡張のパーサー／検査実装（commit `35ebbc36cbfed591e22cd96d519935bf58dea0e1`）
4. `D:\work\arcaea\songs`の実物AFF 1,478譜面と、保存済みArcaea Wikiの公称総ノーツ数

その後、本家3.6.1の`libcocos2dcpp.so`を静的解析し、判定点生成とアーク接続条件を機械語から直接復元した。詳細は[ARCAEA_NATIVE_ANALYSIS.md](ARCAEA_NATIVE_ANALYSIS.md)に分離して記録する。

最重要の結論は次のとおり。

- アーク始点にタップ判定はない。アークを取り始める操作と、スコアへ加算される内部判定点は別物である。
- ロング／アークの内部判定点間隔は、両エディターとも基本的に同じ式を使う。
- 両エディターの表示ノーツ数が違う主因は、接続されたアークを一本の列と認識する許容幅の違いである。
- 実物譜面とWiki総ノーツ数の照合では、Arcade Plus規則がArcCreate規則より明確に一致率が高かった。
- 本家3.6.1モデルはさらに高い1,242/1,252件で一致した。接続条件は「時刻差10ms未満、X差0.1未満、Y完全一致」で、どちらのエディターとも完全には同じでない。この基本処理は5.5.8でも維持されている。
- 接続先を持つアークには、最後の判定時刻を消して一つ前を二回分の加点にする処理がある。総数だけの比較では発見できなかった、本家固有の時刻配置である。

機械集計の全結果は[aff_judgement_analysis.json](docs/references/aff_judgement_analysis.json)、再実行コードは[analyze_aff_judgement_points.py](tools/analyze_aff_judgement_points.py)に保存した。

## AFFで扱う主なイベント

### タップ

```aff
(1000,2);
```

第1引数が判定時刻ms、第2引数がレーンである。一イベントが一判定となる。

### ロング

```aff
hold(1000,2000,2);
```

始点、終点、レーンを持つ。単なる「始点と終点の二判定」ではなく、区間内にBPM依存の判定点が複数入る。

### アーク／トレース

```aff
arc(1000,2000,0.00,1.00,s,1.00,0.50,0,none,false);
```

引数は、始点時刻、終点時刻、始点X、終点X、補間型、始点Y、終点Y、色、効果音、線種フラグである。実物1,478譜面では通常の第10引数に`false`、`true`、`designant`が存在した。

- `false`: 判定のある通常アーク
- `true`: 判定のないトレース
- `designant`: 特殊線種。Arcade PlusとVSCode拡張は認識するが、今回固定したArcCreate版の真偽値パーサーでは通常入力として扱えない

補間型`b`、`s`、`si`、`so`、`sisi`、`siso`、`sosi`、`soso`は軌道形状を決める。判定点数の基本式自体は形状に依存しない。

### アークタップ

```aff
arc(1000,2000,0.00,1.00,s,1.00,1.00,0,none,true)[arctap(1500)];
```

親アークの区間内に独立したタップ判定を置く。総ノーツ数ではアークの内部判定点とは別に一個として数える。VSCode拡張は、アークタップが親アークの範囲外にある場合をエラーとし、判定ありアークにアークタップを付けた場合はトレース扱いになる旨を警告する。

### timinggroup

`timinggroup(...)`は、独自の`timing`列を持つ別レイヤーである。表示速度や逆走などを通常列から独立させられる。`noinput`付きグループ内のノートは判定／配点へ加算しない。`fadingholds`や角度属性は描画・演出を変えるが、通常は判定点の基本間隔式を変えない。

## ロング／アークの判定点間隔

BPMの絶対値を`B`、`TimingPointDensityFactor`を`D`とすると、ArcCreateとArcade Plusの基本間隔`I`は同じである。

```text
B < 255:  I = 30000 / B / D ms
B >= 255: I = 60000 / B / D ms
```

通常の`D=1`なら、255 BPM未満では2分の1拍ごと、255 BPM以上では1拍ごとになる。255を境に式が切り替わるのは譜面仕様上の特殊規則であり、音楽理論上の意味ではない。

```text
150 BPM, D=1 -> 200 ms間隔
300 BPM, D=1 -> 200 ms間隔
150 BPM, D=2 -> 100 ms間隔
```

判定点計算に使うBPMは、両ツールともロング／アークの始点時刻に有効なBPMである。オブジェクト途中の`timing`変更を区間積分していない。このため、VSCode拡張もロング／アークの途中に`timing`が入る配置を検査対象にしており、nesiddo氏の記事も変更点でアークを分割するよう説明している。

実物譜面では、内部に別の`timing`を含むロング／アークを2,440件検出した。ただし、変更時刻が終端の1ms前にある演出用配置なども含む。機械的に「すべて不正」とは判断しない。

## 判定点がどこに置かれるか

区間長を`L = 終点 - 始点`、`T = floor(L / I)`とする。通常の長さのロング、および一本の列の先頭アークは、原則として次の時刻に判定点を持つ。

```text
始点 + I, 始点 + 2I, ... （終点未満）
個数は T - 1
```

接続された後続アークは、接続境界を含む。

```text
始点, 始点 + I, 始点 + 2I, ... （終点未満）
個数は T
```

つまり、アーク列の最初の始点はスコア判定点ではないが、途中で分割された後続アークの接続境界には判定点が一個入る。この「先頭か、接続後続か」の認識差が総ノーツ数の差になる。

上記の通常個数を作れない短い区間は一判定になる。ただし、その時刻は完全には一致しない。

- 短いアーク: 両ツールとも区間中央
- 短いロング: Arcade Plusは区間中央、ArcCreateのコンボ計算上は始点
- 長さ0のアーク: 両ツールとも判定なし

したがって、総ノーツ数の一致だけでは個々の判定時刻まで一致したとは言えない。

BPM 0では実装が一致しない。

- ArcCreate: ロング／アークとも0判定
- Arcade Plus: ロング／アークとも実質1判定（ロングは無限大間隔から中央1個、アークは明示的に始点1個）

実物群には始点BPM 0のロング／アークが358件ある。Arcahv Presentでは、Wikiのロング197に対してArcCreate規則195、Arcade Plus規則197となり、後者が一致した。

### 「1個目と2個目の間だけ広い」ように見える理由

まず、アークの視覚的な始点を「1個目の判定」と数えてはいけない。始点にはタップ判定がなく、最初のスコア判定点は通常`始点 + I`である。以後は`I`間隔になる。始点から最初の加点までの待ち時間を含めて見ると、最初だけ特別に見える。

さらに、次の3層を分ける必要がある。

1. AFFに書かれたアーク区間
2. スコアへ加算される内部判定点の時刻
3. 指がアークから外れたと判断する追従・猶予時間

ArcCreateには、X方向へ動くアークの最初の要求だけ失効時間を短くする処理がある。しかし、これは公称ノーツ数や基本判定点間隔を変える処理ではなく、入力追従の猶予を変える処理である。また同じファイル内で、`FirstJudgeTime`を使うコンボ計算と、始点基準で要求時刻を作るコードが一致していない。ここを本家仕様の証拠にはしない。

現時点の安全な理解は、「通常の内部判定点は等間隔。ただし先頭始点は判定点ではなく、接続境界と入力猶予には特別扱いがある」である。

## ArcCreateとArcade Plusの接続判定差

| 条件 | ArcCreate | Arcade Plus |
|---|---:|---:|
| 時刻差 | 1ms以下 | 10ms未満 |
| X差 | 完全一致 | 0.1未満 |
| Y差 | 完全一致 | 0.01未満 |
| 線種 | 通常同士／トレース同士 | 通常同士／トレース同士 |

ArcCreateは候補が複数ある場合に同色を優先するが、色そのものは接続可否の必須条件ではない。Arcade Plusも色を接続条件にしていない。

Arcade Plusの方が緩い条件なので、接続後続と認識するアークが多く、その境界判定点も増える。実物全体では次の差になった。

- ArcCreate条件で接続後続と認識: 385,672本
- Arcade Plus条件で接続後続と認識: 388,694本
- 総ノーツ数が同じ譜面: 1,353 / 1,478
- Arcade Plus規則の方が1以上多い譜面: 125 / 1,478
- 逆にArcCreate規則の方が多い譜面: 0

## 実物譜面との照合

保存済みArcaea Wiki「ノーツ数順」2ページから曲名、難易度、公称総ノーツ数を読み、`songlist`の英語曲名と実物AFFを対応させた。1,252譜面を比較できた。

| 結果 | ArcCreate規則 | Arcade Plus規則 |
|---|---:|---:|
| Wiki総ノーツ数と一致 | 1,129 | 1,234 |
| 一致率 | 90.2% | 98.6% |

両モデルの答えが異なる109譜面に限定すると、Arcade Plusだけ一致が106譜面、ArcCreateだけ一致が1譜面（World Fragments III(radio edit) Future）、どちらも不一致が2譜面だった。「どちらも不一致」のQuonは同名曲が複数あり、曲名対応が衝突している。Wiki側には譜面版の違いと分類誤りもあり得る。

内訳がすべて掲載されている例では、差はアークに現れる。

| 譜面 | Wiki F/L/A/S | ArcCreate | Arcade Plus |
|---|---|---|---|
| AlterAle Present | 250/157/434/40 | 250/157/432/40 | 250/157/434/40 |
| BADTEK Future | 320/84/244/268 | 320/84/242/268 | 320/84/244/268 |
| Final Step! Present | 156/66/420/42 | 156/66/419/42 | 156/66/420/42 |

WikiのF/L/A/S内訳はページ自身が検証途上を明記しているため、総ノーツ数ほど強い証拠にはしない。

## 各資料から理解できた範囲

### ArcCreate

- AFF読込・編集・描画・入力判定まで持つ。
- ロング／アークの内部判定点数、接続列、判定窓を具体的に実装している。
- 接続条件が本物の公称ノーツ数に対して厳しすぎる例が多数ある。
- 判定要求時刻とコンボ表示時刻に内部不整合があり、本家仕様の唯一の根拠にはできない。

### Arcade Plus

- AFF読込・編集・プレビュー・スコア集計を持つ。
- 判定点の個数と時刻を`JudgeTimings`として明示的に列挙する。
- 接続条件とBPM 0の扱いは、今回の実物公称ノーツ数を高率で再現する。
- プレイヤー入力判定の再現度までは、総ノーツ数一致だけでは証明できない。

### VSCode Arcaea File Format

- 主に構文解析、補完、診断を行う。
- ロング／アークの内部判定点数を計算する実装は見当たらないため、判定点配置の第三の独立証拠ではない。
- 範囲外アークタップ、長さ、線種、途中`timing`などの静的検査には有用である。

### nesiddo氏の記事とArcaea Wiki

- nesiddo氏の記事はAFF各イベント、timinggroup、`noinput`、速度演出、配置上の注意を実作業の観点から説明している。
- 「アーク／ロングのコンボ間隔はBPM依存」という記述は両ツールの式と一致する。
- Arcaea Wikiは、アーク始点にタップ判定がないこと、事前に触れてもよいこと、途中から拾い直せること、トレースは判定対象外であることを説明している。
- どちらも本家クライアントの一次仕様書ではない。実物AFFと公称ノーツ数による反証可能な照合を優先する。

## MAGATU TEMPO FORGEでの採用方針

1. 当面のAFF出力は`timing(...)`だけとし、ノートを自動改変しない。
2. 既存AFFへタイミングを統合する際は、ロング／アーク途中に入る変更を検出して警告する。
3. 将来、判定点や総ノーツ数を表示する場合は、3.6.1と5.5.8で一致した本家の単精度演算、接続条件、重み付き判定点を採用する。
4. 判定点表示では、アーク始点、スコア判定点、入力猶予範囲を別の記号・色で表し、同じものに見せない。
5. `noinput`、トレース、長さ0アーク、`designant`をスコア対象へ誤算入しない。
6. `TimingPointDensityFactor`を無視しない。
7. 本家の実プレイ映像や確定ノーツ数で反例が出た場合は、譜面パスと時刻を記録し、暫定規則を更新する。

アーク入力については、本家3.6.1と5.5.8の機械語から次を確認した。詳細な式、内部座標、関数アドレスは[ARCAEA_NATIVE_ANALYSIS.md](ARCAEA_NATIVE_ANALYSIS.md)を参照する。

- 指が範囲外へ出てもアーク全体が即Missになるわけではない。
- 通常の判定点は、判定点時刻から`min(判定間隔×2, 500ms)`後まで未処理のまま残る。
- その期限前に範囲内へ戻れば未処理点を再取得できるが、Miss済み点は復活しない。
- 方向変化を伴う接続後続アークの最初の点は、`min(判定間隔÷2, 500ms)`へ期限が短縮される。
- 置き始めは保持中よりX方向が広く、120ms先までアーク位置を参照する。
- 軌道外へ動かしただけなら同じ指の所有は残るが、画面から指を離すと`min(判定間隔×4, 1000ms)`だけ、その色を新しい指で取り直せない。
- 入力対象の異色アーク同士が内部入力平面で200未満へ近づくと、両色に500msの受理緩和が入る。この間に指を離しても上記の再取得禁止時間を作らない。
- 色ごとの指所有と交差時の一時緩和は、判定点のMiss期限とは別の仕組みである。
