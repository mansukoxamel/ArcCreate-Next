# Arcaea本家挙動との互換性調査

最終更新: 2026-09-05

## 目的

ArcCreateとArcade Plusが行っているAFFプレビュー／ゲームプレイ再現を、本家Arcaeaの挙動へ近づけるための比較記録である。本家のコードを移植することは目的にしない。同じAFF、再生時刻、入力列を与えたときに、ノーツ位置、表示状態、判定結果が同じになる互換実装を作る。

比較は次の4層を混同せずに行う。

1. AFFから内部ノート列への変換
2. 譜面時刻から画面上の位置・形状への変換
3. タッチ入力から判定状態への変換
4. 判定状態から表示、コンボ、スコアへの変換

## 比較対象の固定

2026-09-05にユーザーのフォークを読み取り専用の一時cloneで確認した。以下のコミットを、この調査の最初の比較基準とする。

| 対象 | ブランチ | コミット |
|---|---|---|
| `mansukoxamel/ArcCreate` | `trunk` | `755c2e8818dab3c8404b3ff997e87373607891cd` |
| `mansukoxamel/Arcade-plus` | `master` | `d157e35cbc3af869094775333a89cf0918aac166` |
| Arcaea 3.6.1 | ARMv7 native | `D:\work\arcaea\APK\3.6.1.mod\lib\armeabi-v7a\libcocos2dcpp.so` |
| Arcaea 5.5.8 | ARM64 native | `D:\work\arcaea\APK\5.5.8.mod\lib\arm64-v8a\libcocos2dcpp.so` |

フォーク側にはまだ変更を加えていない。まず3.6.1で仕様を確定し、意味が確定した処理だけを5.5.8へ対応付ける。4.0.255は、3.6.1のシンボル名から5.5.8の関数を直接対応付けられない場合の橋として使う。

## 第一段階の結論

### 二つのツールは同じ深さの再現ではない

ArcCreateは、描画だけでなく、アークの判定要求、色ごとの指所有、指を離した後の再取得ロック、異色アーク近接時の緩和まで独自に実装している。本家に近い概念はそろっているが、後述する条件と定数の差がある。

Arcade Plusの通常プレビューは、現在時刻からノート位置、経過コンボ、スコアを算出する方式である。`Auto`時の`JudgeArcs()`は、アーク区間に入ればグループを発光させ、終了時刻を過ぎれば処理済みにする。タッチ位置、指ID、色所有、離脱、再取得を本家同様に処理する入力判定機構ではない。したがって、Arcade Plusを本家どおりにするには、定数修正ではなく入力・判定状態機械の追加が必要になる。

### AFF座標からアーク位置への基本変換は一致する

3.6.1の`LogicArcNote::setupArc()`（`0x49ef60`）では、AFF座標を内部座標へ次のように変換する。

```text
Xinternal = 850 * Xaff - 425
Yinternal = 450 * Yaff + 100
```

ArcCreateとArcade PlusはいずれもUnity側の単位を100分の1にし、画面座標系の向きに合わせて次を使う。

```text
Xworld = -8.5 * Xaff + 4.25
Yworld =  4.5 * Yaff + 1.0
```

Xの符号は座標系の左右方向が逆なためで、倍率と中心は本家と一致している。少なくとも通常アークのX/Y基準変換は、見た目の差の主原因ではない。

### アーク8種類の連続曲線式は一致する

本家3.6.1の`LogicArcNote::arcAlgorithmForString()`（`0x5183a0`）は、AFF文字列を次の内部値へ対応させる。

| AFF | 内部値 | X方向 | Y方向 |
|---|---:|---|---|
| `s` | 0 | `S` | `S` |
| `b` | 1 | `B` | `B` |
| `si` | 2 | `I` | `S` |
| `so` | 3 | `O` | `S` |
| `sisi` | 4 | `I` | `I` |
| `sosi` | 5 | `O` | `I` |
| `siso` | 6 | `I` | `O` |
| `soso` | 7 | `O` | `O` |

時間進行率を`t`（0から1）、始点を`a`、終点を`b`とすると、`LogicArcNote::setupArc()`（`0x49ef60`）と`pointThroughSineArcWithAlgorithm()`（`0x49ee10`）が作る各補間は次になる。

```text
S(a,b,t) = a + (b-a)t
B(a,b,t) = a + (b-a)(3t^2 - 2t^3)
I(a,b,t) = a + (b-a)sin(pi*t/2)
O(a,b,t) = a + (b-a)(1-cos(pi*t/2))
```

ArcCreateの`ArcFormula`とArcade Plusの`ArcAlgorithm`は、8種類のX/Y割当と4本の連続式が本家3.6.1に一致する。したがって、`I/O`は左右の「内向き／外向き」ではない。終点との差`b-a`へ掛ける進行関数なので、左右どちらへ動く場合にも同じ意味になる。

- `I`は前半で大きく動き、終点へ近づくほど減速する。
- `O`は始点付近でゆっくり動き、終点へ向けて加速する。
- `B`は始点と終点の両方で傾き0、中央で最も速い。
- 4文字型は先頭2文字がX、末尾2文字がYを指定する。たとえば`siso`はXが`I`、Yが`O`である。

進行関数だけを0から1へ動かした代表値は次のとおりである。これは画面座標ではなく、始点から終点までを何割進んだかを示す。

| `t` | `S` | `B` | `I` | `O` |
|---:|---:|---:|---:|---:|
| 0.25 | 0.250000 | 0.156250 | 0.382683 | 0.076120 |
| 0.50 | 0.500000 | 0.500000 | 0.707107 | 0.292893 |
| 0.75 | 0.750000 | 0.843750 | 0.923880 | 0.617317 |

接線の進行速度は、`S`が常時1、`B`が両端0・中央1.5、`I`が始点`pi/2`・終点0、`O`が始点0・終点`pi/2`となる。このため接続部の見た目を滑らかにしたい場合、文字列名ではなく、接続する二本の終端・始端の接線方向を比較する必要がある。

実物資料`D:\work\arcaea\songs`の1,478個のAFFを集計すると、8種類すべてが使われていた。出現数は`s` 331,257、`si` 85,799、`so` 42,053、`sisi` 34,451、`b` 23,896、`sosi` 21,731、`siso` 20,884、`soso` 11,255である。4文字型は例外的な独自拡張ではなく、実物譜面で通常に使われる正式な型として扱う。

### 連続式が同じでも折れ線の角度は完全には同じでない

本家3.6.1は、通常のアークを時間方向へ分割して描画点を作る。`LogicArcNote::setupArc()`から次を確認した。

- 1000ms未満では、1000ms当たり14分割を基準にする。
- 1000ms以上では、1000ms当たり7分割を基準にする。
- 本家は`N = duration_ms / 1000 * (14または7)`を求め、正規化時間を`1/N`ずつ進め、最後に`t=1`の終点を加える。

ArcCreateとArcade Plusも同じ14／7を採用するため密度の骨格は合う。しかし、両方とも先に区間長を整数ミリ秒へ丸める。ArcCreateは`1000/14`を71msへ四捨五入し、Arcade Plusは71msへ切り捨てる。たとえば500msの短いアークは、本家が7区間なのに対し両フォークは8区間になる。1000msでは本家とArcCreateが7区間、Arcade Plusは142ms切り捨てにより8区間になる。連続式は同じでも、折れ線の節位置と各面の角度が少し異なる。

さらに本家は、AFF端点を内部座標へ変換した時点で次を0方向へ整数化してから曲線を作る。

```text
Xinternal = trunc(850 * Xaff - 425)
Yinternal = trunc(450 * Yaff + 100)
```

両フォークはfloatのまま補間するため、通常の100分の1ワールド換算では端点と中間点に最大約0.01の差が残る。大きな形状差ではないが、同一画面をピクセル単位で重ねる試験では無視できない。

最終的な画面上の角度はX/Y補間だけでは決まらない。Z距離、カメラ射影、端末アスペクト比、手前側クリップ、アーク頭・末尾、線幅、影、透明度も作用する。前節で確定したZ距離倍率の差があるため、「X/Y式が一致する」だけでは現在の両フォークの見た目が本家と一致するとはいえない。

### 3.6.1の通常カメラ基準値も一致する

3.6.1の`CameraController::init()`（`0x4f79f0`）から、通常画面と縦長側の二つのカメラプロファイルを確認した。内部座標をUnity側の100分の1へ換算すると次になる。

| 項目 | 通常側 | 縦長側 |
|---|---:|---:|
| 垂直FOV | 50度 | 65度 |
| 基準解像度の高さ | 960 | 720 |
| カメラ位置 | `(0, 9, 9)` | `(0, 9, 8)` |
| 注視点 | `(0, -5.5, -20)` | 同左 |
| X回転相当 | 約26.565度 | 約27.378度 |

本家のnear clip引数は内部値1、far clip引数は内部値10000である。ただし、Unity側は軸ごとの単位変換が一律ではないため、この二値は投影結果の照合が終わるまで単純に100分の1へ換算しない。

ArcCreateとArcade Plusはいずれも、FOV、位置、注視点／回転を同じ値で実装している。通常カメラの主要な基準値も、見た目の差の主原因ではない。

一方、3.6.1は二つのプロファイルを条件分岐で選ぶ。Arcade Plusも`Is16By9`で二者択一するが、ArcCreateはアスペクト比からFOV、Z位置、X回転を連続補間する。16:9と4:3の基準点では一致するが、その中間や範囲外の画面比率ではArcCreateだけ本家3.6.1と異なる値になる。この連続補間はエディターとしては滑らかだが、「3.6.1と同じ画面」を選べる互換モードとは分けるべきである。

### 床位置は「BPM区間の積分」である

3.6.1の`LogicChart::getZOffsetAtTime()`（`0x517b84`）は、対象timinggroupの各`LogicTimingEvent`について、対象時刻までの経過時間をイベントの`+0x24`にある時間／距離係数で割り、区間ごとに加算する。`LogicTimingEvent::init()`（`0x4b65f4`）では同係数をBPM、速度倍率、定数60から作る。

したがって本家のノーツ移動は、単純な「現在BPM × ノートまでの時間」ではなく、現在時刻からノート時刻までをまたぐ全timing区間の速度積分である。ArcCreateの`TimingGroup.GetFloorPosition()`とArcade Plusの`CalculatePositionByTimingAndStart()`も同じ種類の区間積分を行う。ただし、次節のとおり距離倍率は一致しない。

### ハイスピードからZ距離への式

3.6.1の`SongManager::loadLogicChartForSong()`（`0x53737c`）は、保存されたハイスピード整数をfloatへ変換して10で割り、その値を`LogicChart::create()`へ渡す。たとえば保存値50は表示速度5.0として扱われる。

`LogicTimingEvent::init()`（`0x4b65f4`）は、BPMを`B`、表示速度を`S`とすると、内部に`B * S`と`60 / (B * S)`を保存する。`LogicChart::getZOffsetAtTime()`（`0x517b84`）は各timing区間について経過ミリ秒を後者で割るため、本家の生Z距離は次の式になる。

```text
Zofficial = -sum(delta_ms * B * S / 60)
```

本家のX/Y座標、カメラ位置とフォーク側の対応と同じ100分の1換算で比較する場合は、`Zofficial_world = -sum(delta_ms * B * S / 6000)`となる。

一方、二つのフォークはプロジェクトの基準BPMで正規化している。

```text
ZarcCreate  = -sum(delta_ms * B / BaseBpm * 30.0 * S / 1000)
ZarcadePlus = -sum(delta_ms * B / BaseBpm * 26.5 * S / 1000)
```

Arcade Plusの`settingVelocity / 3 * 2.65f`は、`settingVelocity`が整数なので`/ 3`も整数除算である。通常の0.1刻み速度では上式になるが、それ以外の値を直接設定するとさらに量子化される。

本家内部座標からUnityワールド座標への最終換算と射影は別層なので、ここでは画面上のピクセル倍率まで同一単位だとは断定しない。しかし、フォーク間で30と26.5が異なること、両フォークにだけ`BaseBpm`正規化があることは確定している。カメラ値を変えてこの差を相殺すると、別BPM区間や別アスペクト比で再びずれる。互換化では、距離関数とカメラ関数を分けて試験する。

### camera命令の`s`は本家では線形

3.6.1の`CameraController::moveCameraBy()`（`0x4f7c14`）は、まず一定速度の`MoveBy`を作り、camera種別が`qi`のときだけcubic-in、`qo`のときだけcubic-outで包む。それ以外は元の`MoveBy`をそのまま使う。したがってAFFの`s`は線形移動である。

Arcade Plusは`s`へ線形式を使うため3.6.1と一致する。ArcCreateは`CameraEvent.PercentAt()`で`s`へsmoothstep型の`ArcFormula.B()`を使うため、開始と終了で減速・加速が入り、本家とは明確に異なる。

### アーク追従tiltは4%／2%補間

3.6.1の`CameraController::setCameraTilt()`（`0x4f80b0`）は入力を`[-1, 1]`へ制限し、0.05倍した値を目標傾斜にする。現在値から目標値への差に対し、追従中は1更新ごとに4%、目標が0の復帰中は2%を加える。カメラのupベクトルには、この現在傾斜値を反映する。

Arcade Plusの実装は、120Hz換算で追従`4.8 * deltaTime = 0.04`、復帰`2.4 * deltaTime = 0.02`となり、本家の二つの係数と一致する。ArcCreateは追従・復帰とも`6.0 * deltaTime`で、復帰時の半速処理もない。したがって、アークへ傾く速さと中央へ戻る余韻はArcade Plusの方が本家3.6.1に近い。

### 表示更新で確定した範囲と未確定部分

3.6.1の`GameModel::updateVisibleNotes()`（`0x4a98f8`）は、timinggroupごとに現在時刻と120ms先のZオフセットを求め、各ノートの`updateZPosition()`を呼ぶ。`LogicNote::updateZPosition()`（`0x48ad14`）は、開始・終了それぞれの基準Zへ現在オフセットを足し、整数へ変換して保存する。tap、hold、arc、arctapは、この共通Z更新を土台に個別描画を行う。

ただし、この120ms先の値は可視範囲走査や入力処理でも使われるため、「120ms前から表示する」または「120ms後に消す」という単独の表示寿命とはまだ断定しない。`RenderNote::update()`では、論理ノート側の完了条件に加えて内部値300を越えた場合に描画を無効化する経路を確認したが、その内部値の意味は未確定である。ArcCreateの前方100／後方53.5と20単位フェード、Arcade Plusの`LostDelay = 120ms`を本家値として採用してはならない。ここは次段階でノート種別ごとに追跡する。

## 現時点で確定した相違点

### 1. アーク接続条件

本家3.6.1の接続条件は次のとおりである。

```text
abs(previous.endTiming - next.timing) < 10ms
abs(previous.xEnd - next.xStart) < 0.1
previous.yEnd == next.yStart
previous.trace == next.trace
```

| 実装 | 時刻 | X | Y | trace |
|---|---:|---:|---:|---:|
| 本家3.6.1 | `< 10ms` | `< 0.1` | 完全一致 | 一致 |
| ArcCreate | `<= 1ms` | 完全一致 | 完全一致 | 一致 |
| Arcade Plus | `< 10ms` | `< 0.1` | `< 0.01` | 一致 |

ArcCreateは時刻とXが本家より厳しすぎる。Arcade PlusはYが本家より緩い。この差は単なる表示上の連結だけでなく、始点判定点、指所有の継承、アーク頭の表示、判定数へ波及する。

### 2. ArcCreateの初回取得位置

本家3.6.1は、まだ保持していない指がアークを取得する際、現在時刻ではなく120ms先のアーク位置までを候補として評価する。初回取得の内部入力平面範囲はXが厳密に`-302 < dx < 302`、Yが厳密に`-250 < dy < 250`である。保持中は現在位置を使い、Xが`-190 < dx < 190`、Yが`-250 < dy < 250`へ狭くなる。

ArcCreateの`TouchInputHandler.ArcCollide()`は、初回取得と保持中を分けず、現在時刻の`WorldSegmentedXAt/YAt`を使う。基本ワールド範囲`ArcHitboxX = 1.9`、`ArcHitboxY = 2.5`は本家の保持中190/250に対応するが、初回取得の120ms先とX=302相当を再現していない。

さらにArcCreateは、ワールド座標の範囲または画面へ射影した範囲のどちらか一方が通れば衝突とする。本家3.6.1で確認した通常経路は内部入力平面の範囲比較であり、境界値ちょうどを除外する。ArcCreateは`<=`を使う。このため、取得開始の時刻、カメラ変形時、判定範囲の端で結果が変わり得る。

### 3. ArcCreateの判定点Miss猶予

本家の通常判定点は`point + min(2I, 500ms)`まで、方向が変わる接続後続アークの最初の点だけは`point + min(I/2, 500ms)`まで回収可能である。

ArcCreateは、X始点とX終点が異なる全アークの最初の要求に短い猶予を適用する。これは本家の「接続後続かつ接続部で方向が変化」という選択条件とは異なる。判定点時刻の基準にも`Timing`と`FirstJudgeTime`が混在しており、短区間と接続区間では個別の回帰試験が必要である。

### 4. ArcCreateの異色アーク近接緩和

本家3.6.1は、入力対象の異色アーク同士が内部入力平面で200未満まで近づいたフレームに、両色へ「どの指でも受理」する上書きを設定し、最後の設定から500ms維持する。

ArcCreateにも異色アーク衝突時の全色graceがあるが、持続時間は`ArcGraceDuration = 600ms`である。また衝突判定は、通常のアーク入力と同じ画面／ワールドの複合範囲を利用する。本家と目的は同じだが、持続時間と幾何条件は一致していない。

### 5. 指を物理的に離した後のロック

この部分はArcCreateが本家にかなり近い。本家は画面から指を離した後、同じ色の新しい指取得を`trunc(min(4I, 1000ms))`だけ拒否する。ArcCreateも`min(round(4I), 1000ms)`を使う。

残る差は整数化方法である。本家3.6.1と5.5.8は小数部を0方向へ切り捨てる。ArcCreateは`Mathf.RoundToInt`なので、判定間隔が整数でないBPMでは1msずれる場合がある。互換実装では切り捨てを使う。

### 6. Arcade Plusには手入力判定の比較対象がない

Arcade Plusの`JudgeArcs()`は`Auto`時だけ呼ばれ、現在時刻がアーク区間内なら発光、終了後なら処理済みにする。`ArcScoreManager`も入力結果ではなく「現在時刻以前にある判定点数」からコンボとスコアを作る。

よって、Arcade Plusについて本家と比較できる現状の対象は、主に次の層である。

- AFFの読み書き
- ノートの時間位置と曲線
- カメラ、床位置、ハイスピード
- メッシュ、頭、末尾、影、透明度
- autoplay表示

手入力、Miss、再取得、色所有、実スコアを忠実化する場合は、ArcCreateまたは本家解析結果を仕様として新しい状態機械を設ける必要がある。

### 7. 見た目を変える確定差分

今回の第二段階で、目視差へ直接つながる次の差を確定した。

| 項目 | 本家3.6.1 | ArcCreate | Arcade Plus |
|---|---|---|---|
| Z距離 | 生座標は`delta * BPM * speed / 60`（100分の1換算では`/6000`） | `BaseBpm`正規化、係数30 | `BaseBpm`正規化、係数26.5 |
| camera `s` | 線形 | smoothstep | 線形 |
| tilt追従 | 1更新4% | `6 * deltaTime` | 120Hz換算4% |
| tilt復帰 | 1更新2% | 追従時と同速 | 120Hz換算2% |

まずZ距離関数を本家式へ合わせ、次にcamera `s`とtiltを合わせる。この順序なら、距離誤差をカメラで隠すことがない。

## 実装へ進む前の試験単位

いきなり見た目を目視で直すと、カメラとノート座標の誤差を相互に打ち消してしまう。次の純粋関数・状態遷移から固定する。

1. `timing events + t0 + t1 + speed -> floor distance`
2. `AFF x/y + curve + progress -> internal position`
3. `arc A + arc B -> connected / not connected`
4. `touch history + arc + time -> acquired / retained / released / locked`
