# Arcaea本家クライアント ネイティブ解析記録

調査開始日: 2026-09-05

## 目的

MAGATU TEMPO FORGEが出力するAFFを、本家クライアントが実際にどう解釈するか確定する。まず関数名が残る3.6.1で基準実装を復元し、次に5.5.8で同じ処理を特定する。4.0.255は、ARM32の3.6.1からARM64の5.5.8へ直接対応付けできない箇所だけを橋渡しに使う。

調査対象はapktoolで展開されたAndroidパッケージであり、C++ソースコードではない。いずれもUnity/IL2CPPではなく、Cocos2d-x系の`libcocos2dcpp.so`にゲーム処理がコンパイルされている。解析は所有するローカルファイルに対する読み取り専用の静的解析として行い、バイナリ自体はリポジトリへ複製しない。

## 3.6.1で確定した判定点生成

### 判定間隔

`LogicLongNoteBase::init(...)`（Thumb実アドレス`0x5556e0`）は、始点で有効な`LogicTimingEvent`のBPMと`TimingPointDensityFactor`から、単精度浮動小数点で判定間隔を作る。

```text
B = abs(BPM)
factor = 2.0  (B < 255)
factor = 1.0  (B >= 255)
interval = float32(float32(float32(60000 / B) / factor) / density)
```

これまでArcCreateとArcade Plusから得た式自体は正しかった。ただし本家3.6.1は各段階を`float32`へ丸める。境界付近では、倍精度で最後に`floor`するだけの再実装と判定数が変わり得る。

### 基本判定点

`LogicLongNoteBase::setupJudgementTimingPoints(bool)`（`0x555748`）の処理は次のとおり。

1. 判定点配列を空にする。
2. `total = trunc(float32(duration) / interval)`を得る。
3. 通常のロングまたはアーク列先頭は添字1から、接続された後続アークは添字0から始める。
4. 各時刻を`trunc(float32(start + float32(index * interval)))`で整数msへ変換し、終点未満だけを追加する。
5. 一点も作れず長さが0でなければ、単精度計算した区間中央へ一点置く。
6. 長さ0なら一点も置かない。

`LogicChart::init(...)`（`0x516574`）は全ロングノートに対し仮想関数スロット`+0x28`からこの処理を呼ぶ。アークの場合は先に`setupArc()`を呼び、`LogicArcNote + 0x70`の「前のアークから接続された」フラグを引数に渡す。したがって、列先頭の視覚的始点は加点点ではないが、接続された後続アークの境界は加点点になる。

### 接続先を持つアークの二重点

`LogicArcNote::setupJudgementTimingPoints(bool)`（`0x49f7e0`）は基本判定点を作った後、そのアークに接続先があり、次を満たす場合に末尾を調整する。

```text
trunc(float32(duration - 2) / interval)
    == trunc(float32(duration) / interval) - 1
```

判定点が2個以上なら、最後の判定点を配列から除き、一つ前の`JudgementPoint + 4`を`1`から`2`へ変える。これはノーツ数を減らす処理ではない。`LogicLongNoteBase::getJudgementPointCountToTime(int)`（`0x518654`）と`checkComboCount(int)`（`0x4aae82`）はこの値を加算するため、二回分の加点を一つ前の時刻へ束ねる処理である。

この処理により、表示上は一定間隔の列でも、一部の境界直前では「判定時刻が一つ抜け、前の判定が二回分」になる。ユーザーが指摘した、アークの最初と次以降で判定間隔が違って見える現象を説明し得る本家側の具体的処理である。入力猶予の処理とは別である。

## 3.6.1で確定したアーク接続条件

`LogicChart::calculateNoteConnections()`（`0x5170a8`）は、前アークの終点と次アークの始点に対して次をすべて要求する。

- 時刻差の絶対値が9ms以下、すなわち10ms未満
- X差の絶対値がdouble定数`0.1`未満
- Yが単精度値として完全一致
- 通常アーク同士、またはトレース同士

Xは前アークの終点`NotePosition`と次アークの始点`NotePosition`の`+0x10`を比較する。Yは`LogicArcNote + 0x78`の終点Yと`+0x74`の始点Yを比較する。`LogicArcNote::init(...)`（`0x49ed1c`）の引数から、この対応を確認した。

色は接続可否条件ではない。方向が変わる接続では別フラグを立てるが、接続自体は成立する。

従来資料の「Arcade PlusはY差0.01未満」という規則は本家3.6.1とは一致しない。本家3.6.1は、時刻とXはArcade Plusに近く、Yだけ完全一致という組合せである。

## 4.0.255と5.5.8の照合

### 4.0.255

3.6.1の`LogicLongNoteBase::init`を特徴づける隣接定数`255.0`と`60000.0`は、4.0.255の`.text`内にも一組だけ存在する。その直前のThumb関数`0x826dfc`を逆アセンブルすると、3.6.1と同じ順序で次を行っていた。

- `LogicTimingEvent + 0x1c`からBPMを読む
- 絶対値を255.0と比較する
- 60000.0をBPM、2または1、DensityFactorの順で除算する
- 結果をオブジェクト`+0x58`へ保存する

クラスレイアウト変更により判定間隔の保存位置は3.6.1の`+0x50`から`+0x58`へ移ったが、式と単精度演算順は同じである。これにより、4系を3系と5系の橋として使えることを確認した。

### 5.5.8

5.5.8では関数名が削られているため、残存するItanium C++ RTTIから型情報と仮想関数表を復元した。

- `LogicLongNoteBase`型名文字列: `0x38621d`
- `LogicLongNoteBase` typeinfo: `0x13ea8d0`
- 基底クラス仮想関数表ヘッダ: `0x1483108`、関数列は`0x1483118`から
- `LogicArcNote`型名文字列: `0x3d85e8`
- `LogicArcNote` typeinfo: `0x1490660`
- アーク仮想関数表ヘッダ: `0x1487c30`、関数列は`0x1487c40`から

3.6.1と同じ仮想関数スロット順から、次の関数を対応付けた。

| 役割 | 5.5.8 AArch64アドレス |
|---|---:|
| `LogicLongNoteBase::init(...)` | `0xda4760` |
| `LogicLongNoteBase::setupJudgementTimingPoints(bool)` | `0x11ff78c` |
| `LogicArcNote::setupJudgementTimingPoints(bool)` | `0x70c774` |
| `LogicChart::calculateNoteConnections()`相当 | `0x6213c8` |

5.5.8の`LogicLongNoteBase::init`は、`60000.0`をレジスタ即値`0x476a6000`、`255.0`を`0x437f0000`として組み立てる。比較、2/1の選択、3段の単精度除算は3.6.1と同じで、判定間隔はオブジェクト`+0x70`へ保存される。

基底の判定点生成も、次のすべてが3.6.1と一致する。

- 接続後続フラグを反転して開始添字0/1を選ぶ
- `float32(duration / interval)`をゼロ方向へ整数化する
- `float32(start + index * interval)`をゼロ方向へ整数ms化する
- 終点未満だけを追加する
- 空かつ長さ非0なら中央一点、長さ0なら0点
- `JudgementPoint`は12バイトで、時刻、重み、状態byteを持つ

アーク固有補正も、`duration-2`の条件、最後の12バイトを除く処理、一つ前の重みを2へ変える処理まで一致する。5.5.8では接続先配列`+0x118`を調べ、対象となる接続先がある場合に補正する。

`calculateNoteConnections()`相当も命令列から特定できた。double定数`0.1`は`0x46a548`にあり、条件は3.6.1と同じである。

- 時刻差の絶対値が9ms以下
- X差の絶対値が0.1未満
- Yが単精度で完全一致
- 通常アーク／トレースの種別が一致

したがって、今回最重要だった「ロング／アーク判定点の基本式、アーク接続、境界で二回分を一時刻へ束ねる処理」は3.6.1から5.5.8まで維持されていることを、本家バイナリ同士で確認できた。旧AFFが残っているという間接証拠だけに依存した結論ではない。

## アークから指が外れた場合の処理

ここでは、スコアを発生させる「判定点」と、指が現在アークを保持しているかを表す「入力追従」を分けて扱う。両者を同じ点と考えると、アーク始点、指の離脱、拾い直しを誤実装する。

### 1フレーム内の状態更新

3.6.1の`LogicLongNoteBase::updateZPosition()`（`0x49fcb6`）は、毎フレーム初めに現在の接触状態2byte（`LogicArcNote + 0x44/+0x45`）を0へ戻す。その後、`GameModel::checkArcInputs()`（`0x4aa1c0`）が、そのフレームに存在する全タッチと全アークを照合する。範囲内で色の所有条件も通れば、`LogicArcNote::setBeingTouched()`（`0x49fa20`）が同じ2byteを`1/1`へ戻す。

したがって、保持状態は一度立てたまま残るラッチではない。毎フレーム、現在の指位置から再構築される。

1. フレーム開始時に「現在接触中」を消す。
2. 全タッチをアークの現在位置と照合する。
3. 範囲内かつ受理可能な指なら「現在接触中」を立てる。
4. 接触中なら未処理判定点を加点し、非接触なら期限切れ判定点をMissにする。

このため、指が範囲外へ出ても、その瞬間にアーク全体が即Missになるわけではない。範囲内へ戻れば次のフレームで再取得される。ただし、戻る前にMiss確定して処理済みになった判定点は復活しない。

### 加点とMiss確定の時間窓

判定点時刻を`t`、判定間隔を`I`、現在の譜面時刻を`p`とする。

接触中の`GameModel::checkComboCount()`（`0x4aae82`）は、次を満たす未処理判定点を加点済みにする。

```text
t <= trunc(p + I / 2)
```

非接触中の`GameModel::checkMissCount()`（`0x4aaef8`）は、通常の未処理判定点について次を満たすものをMiss済みにする。

```text
t <= p - min(2I, 500ms)
```

言い換えると、通常点は`t + min(2I, 500ms)`付近までに保持を戻せば、まだ処理されていない点を回収できる。実際の確定フレームは整数ms化とフレーム更新周期の影響を受ける。

接続境界でXまたはY方向が変化した後続アークの最初の点だけは短い期限を使う。`LogicChart::calculateNoteConnections()`（`0x517224`）が後続アーク`+0x4c`へ立てたフラグを`checkMissCount()`が参照し、次でMissにする。

```text
t <= p - min(I / 2, 500ms)
```

これは判定点の配置を変える規則ではなく、曲がり角の後続アークを取り損ねた場合のMiss猶予だけを短くする規則である。

例として150 BPM、DensityFactor 1では`I = 200ms`なので、保持中は100ms先まで加点対象になり、通常点の離脱猶予は400ms、方向変化後の先頭点は100msになる。60 BPMなら`I = 500ms`なので、通常点は上限の500ms、方向変化後の先頭点は250msになる。

### 指を置き始める範囲と保持中の範囲

3.6.1の`GameModel::isArcInRangeOfTouch()`（`0x4aac38`）と`inputPlaneTouchWithinRangeOfArc()`（`0x4ab4d0`）では、最初に指を置く場合と、保持中の追従で範囲が異なる。

| 版・状態 | 時間方向 | X方向 | Y方向 |
|---|---:|---:|---:|
| 3.6.1 置き始め | アーク位置を120ms先まで参照 | 目標から`-302 < dx < 302` | 目標から`-250 < dy < 250` |
| 5.5.8 置き始め | アーク位置を120ms先まで参照 | 目標から`-302 < dx < 302` | 目標から`-310 < dy < 250` |
| 3.6.1／5.5.8 保持中 | 現在時刻のアーク位置 | 目標から`-190 < dx < 190` | 目標から`-250 < dy < 250` |

X/Yは画面ピクセルではなく、ゲーム内部の入力平面座標である。境界値ちょうどは比較から外れる。`allowsMemes`モードでは画面・座標スケールと奥行き条件が追加されるため、上表をそのままピクセルへ換算してはいけない。

トレースは`LogicArcNote::canBeTouched()`（`0x49fc3a`）が偽を返すため、この入力判定とMiss判定の対象にならない。

### 色と指の所有関係

通常アークは色ごとの`LogicColor`を通して指を受理する。3.6.1の`LogicColor::acceptsTouch()`（`0x4a56ac`）から、次を直接確認した。

- 同じ色がすでに所有している同じ指は継続して受理する。
- 未所有の色は、他色に所有されていない指を取得できる。
- 別の指で所有済みの色や、別色に所有済みの指は原則として受理しない。
- 指を離したイベントでは`GameModel::endArcTouches()`（`0x4a959c`）が全色へ通知し、対応する指IDの所有を解除する。
- 接続先を持たないアークの完了時には`LogicArcNote::completionTrigger()`（`0x49f9ec`）も色の所有を解除する。接続列では所有状態を次へ渡す。

範囲外へ動かしただけの場合と、指を画面から離した場合は同じではない。前者は指IDの所有が残るため、同じ指を範囲内へ戻せば直ちに再取得できる。後者では`LogicColor::clearTouchIfAssociated()`（`0x4a5798`）が離した時刻を記録し、`LogicColor::acceptsTouch()`は次の時間が過ぎるまで、その色への新しい指の取得を拒否する。

```text
画面から指を離した後の再取得禁止時間 = trunc(min(4I, 1000ms))
```

これは上記のスコア判定点Miss猶予`min(2I, 500ms)`とは別状態である。前者は色と指の再関連付け、後者は各判定点がMiss済みになる期限を制御する。

`GameModel::checkArcIntersections()`（`0x4a9d10`）は、現在時刻がアーク区間内にあり、入力対象の異色アーク同士の現在位置が内部入力平面で200未満まで近づく場合、両色へ一時的な「どの指でも受理」上書きを設定する。上書きは最後に設定した時刻から500msで失効する。上書き中に指を離した場合は`clearTouchIfAssociated()`が上記の再取得禁止時刻を記録しない。これは交差・近接する赤青アークで指の所有が衝突することを避ける緩和であり、一本のアークのスコア判定点を増減させるものではない。

### 5.5.8での維持確認

5.5.8でも、構造体オフセットは変わったが同じ状態遷移を確認した。

| 役割 | 3.6.1 | 5.5.8 |
|---|---:|---:|
| アーク接触状態 | `+0x44/+0x45` | `+0x64/+0x65` |
| 判定間隔 | `+0x50` | `+0x70` |
| 方向変化後の先頭点フラグ | `+0x4c` | `+0x6c` |
| 判定点配列 | `+0x58` | `+0x78` |
| `canBeTouched()`相当 | `0x49fc3a` | `0x13b7714` |
| `setBeingTouched()`相当 | `0x49fa20` | `0xfa7248` |
| `LogicColor::acceptsTouch()`相当 | `0x4a56ac` | `0xb133b8` |
| 毎フレームの接触状態リセット | `0x49fcb6` | `0xd98328` |
| `checkMissCount()`相当 | `0x4aaef8` | `0x1126b0c` |

5.5.8のMiss処理は、通常点の`min(2I, 500ms)`と、方向変化後の先頭点の`min(I/2, 500ms)`を同じ順序で計算する。接触中の加点走査は`0x86f2a8`以降へインライン展開されているが、`p + I/2`までの未処理点を後ろから連続して処理する点も同じである。`LogicColor::acceptsTouch()`相当も`fcvtzs`で`min(4I, 1000ms)`を整数化し、指を離した時刻からの経過時間と比較している。したがって、離脱後の回収可能時間、画面から指を離した後の色再取得禁止、処理済み点を復活させない基本設計は3.6.1から5.5.8まで維持されている。

5.5.8の`GameModel::checkArcInputs()`相当（`0x12815f4`）は、保持判定を`isArcInRangeOfTouch()`相当（`0x67da7c`）、入力平面比較を`inputPlaneTouchWithinRangeOfArc()`相当（`0x83f65c`）へ委譲する。後者の定数100、212、90、250、60と厳密比較から、保持中はX±190・Y±250、初回はX±302・Y下側310／上側250となる。3.6.1から変わったのは初回取得のY下側だけである。

5.5.8の`GameModel::checkArcIntersections()`相当（`0xe1040c`）は、異色かつ入力対象のアーク同士について現在位置間の距離を求め、200.0未満の場合だけ両色の受理上書きを設定する。`LogicColor::update()`相当（`0x1289a18`）は設定時刻へ500を加えて失効判定するため、距離と猶予は3.6.1から変わっていない。

### 譜面支援ソフトへ実装する際の要点

- アーク始点、内部判定点、現在の入力許容範囲、Miss確定期限を別のデータとして扱う。
- 「指が外れた」をアーク全体の即時Missへ変換しない。判定点ごとに未処理／加点済み／Miss済みを持つ。
- 再取得では未処理点だけを回収し、Miss済み点を復活させない。
- 方向変化を伴う接続後続アークの最初の点には、通常点より短いMiss期限を適用する。
- 軌道外へ動かす場合と、画面から指を離す場合を区別する。後者だけ色の再取得禁止時間が発生する。
- 色ごとの指所有と、交差時の一時緩和をスコア判定点の時間窓と混同しない。

## ノート表示の対応付け

3.6.1は動的シンボルから描画更新関数を直接特定できる。5.5.8は関数名が削除されているため、残存RTTI名からtypeinfoと仮想関数表を復元し、Cocos2d-x基底関数に続く各クラス固有スロットを対応付けた。

| 役割 | 3.6.1 ARMv7 | 5.5.8 AArch64 |
|---|---:|---:|
| tap更新 | `0x55ae80` | `0xbeb210` |
| arctap更新 | `0x55cd90` | `0xc0d8fc` |
| hold更新 | `0x481dbc` | `0x123f078` |
| arc更新 | `0x4f9cc4` | `0xf4a510` |
| arc手前切断 | `0x4f9b94` | arc更新内と補助呼出へ再配置 |

tapとarctapは両版とも内部Zの`-9000`と`-1000.0f`を使い、`(-9000 - Z) / -1000`を0～1へ制限する。したがってArcCreate単位での表示開始はZ=-90、最大不透明度へ到達するのはZ=-80である。不透明度の上限もtap=255、arctap=240で一致する。

arcセグメントは進行率を0～1へ制限し、`75 + 150 * progress`で不透明度を決める。3.6.1の通常arcと5.5.8の継続arcはZ=-95～-85、5.5.8の長さ0のslamはZ=-90～-80を使う。後者は`0xf4a790`以降の始終時刻比較と9500/9000の選択から確認した。

holdは開始後に始点Zを0へ置き換え、arcは消化済みセグメントを隠して最初の残セグメント始点を判定面へ移す。命中済みtap/arctapと完了済み長押しは、完了フラグと通常描画モードが揃ったときに描画を無効化する。これらの基本状態遷移は5.5.8でも維持されている。
